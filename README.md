# rplib

**Rust bindings and a safe robot framework for FRC's WPILib HAL.**

rplib lets you write FRC robot code in Rust. It wraps WPILib's Hardware Abstraction Layer (HAL), the same C API that WPILib's own Java and C++ libraries are built on, in safe, idiomatic Rust types. Robot programs never touch raw handles, status codes, or `unsafe`.

> ⚠️ **Very early, unfinished project.** rplib is nowhere near complete. Right now it's at the stage of running small example programs in simulation. It has never run on real robot hardware, most of WPILib's functionality isn't wrapped yet, and the API will change without notice. See [Status](#status) for what exists so far.
>
> This is a learning/side project, not affiliated with or endorsed by WPILib or *FIRST*. 
>
> Although it would be pleasing to see rplib go far, <u>**please**</u> don't put it on a competition robot.

```rust
use rplib::{run, DigitalOutput, Robot, XboxAxis, XboxController};

struct MyRobot {
    xbox: XboxController,
    led: DigitalOutput,
}

impl Robot for MyRobot {
    fn teleop_periodic(&mut self) {
        let forward = -self.xbox.axis(XboxAxis::LeftY) > 0.5;
        self.led.set(forward).unwrap();
    }
}

fn main() {
    run(|| MyRobot {
        xbox: XboxController::new(0),
        led: DigitalOutput::new(0).unwrap(),
    });
}
```

## Crates

| Crate | What it is |
|---|---|
| `rphal-sys` | Raw FFI bindings to the WPILib HAL, generated by `bindgen` at build time. Everything is `unsafe`. |
| `rplib` | The safe layer: the robot runner, hardware types, and Driver Station input. This is what robot code uses. |

## Features

- **Robot runner.** `run()` initializes the HAL, drives a 20 ms periodic loop, reports mode to the Driver Station, and handles the main-thread requirements of the simulation GUI for you.
- **`Robot` trait** with `robot_init`, `disabled_periodic`, `teleop_periodic`, and `auton_periodic`. Override only what you need.
- **Ownership-based hardware.** Each hardware type owns its HAL handle and frees it on `Drop`. Types are deliberately not `Clone`, so a port can't be freed twice or used after it's released.
- **Errors as `Result`.** HAL status codes become `HalError`, which includes the HAL's own error message.
- **Typed controller input.** `XboxController` uses enums for buttons and axes, so `xbox.button(XboxButton::A)` compiles and `xbox.button(47)` doesn't. A generic `Joystick` with raw indices covers everything else.
- **Panics fail loudly.** A panic anywhere, including the robot thread, exits the whole program instead of leaving a running GUI on top of dead robot code.

## Getting started

### 1. Prerequisites

- Rust (stable), via [rustup](https://rustup.rs)
- `libclang`, which `bindgen` needs:
  - **macOS:** Xcode Command Line Tools (`xcode-select --install`)
  - **Arch:** `sudo pacman -S clang`
  - **Debian/Ubuntu:** `sudo apt install libclang-dev`

### 2. Get the WPILib libraries

The HAL headers and prebuilt libraries come from WPILib's Maven repository:

```
https://frcmaven.wpi.edu/artifactory/release/edu/wpi/first/
```

Use the WPILib version for your platform from the [platform table](#platform-support): `2026.1.1` on macOS, `2026.2.1` on Linux. All artifacts on one machine must use **exactly the same version**, including the headers. Mixing versions causes confusing symbol errors.

In the tables below, replace `<version>` with your platform's version.

**To build (required):**

| Artifact | Path under `edu/wpi/first/` | Zips |
|---|---|---|
| HAL | `hal/hal-cpp/<version>/` | `headers` and your platform |
| wpiutil | `wpiutil/wpiutil-cpp/<version>/` | `headers` and your platform |

Platform zips are `osxuniversal` on macOS and `linuxx86-64` on Linux.

Extract the headers so that `hal/HAL.h` and `wpi/...` resolve from the include directories, and put the platform libraries where `rphal-sys/build.rs` expects them:

```
rphal-sys/headers/
├── hal/
│   ├── include/hal/HAL.h ...
│   └── lib/<platform>/libwpiHal.{dylib,so}
└── wpiutil/
    ├── include/wpi/...
    └── lib/<platform>/libwpiutil.{dylib,so}
```

**For the simulation GUI (optional, recommended):**

| Artifact | Path under `edu/wpi/first/` |
|---|---|
| Sim GUI | `halsim/halsim_gui/<version>/` |
| wpimath | `wpimath/wpimath-cpp/<version>/` |
| ntcore | `ntcore/ntcore-cpp/<version>/` |
| wpinet | `wpinet/wpinet-cpp/<version>/` |

Put all of these libraries in the same folder as `libhalsim_gui`.

### 3. Build

```sh
cargo build
cargo test
```

### 4. Run an example in simulation

```sh
HALSIM_EXTENSIONS=/path/to/libhalsim_gui.dylib \
  cargo run -p rplib --example joystick
```

Use the `.so` file on Linux. In the sim GUI:

1. Drag **Keyboard 0** from *System Joysticks* onto **Joystick[0]**.
2. Click **Teleoperated** under *Robot State*.
3. Focus the sim window and press keys. The key mapping is under **DS → Keyboard 0 Settings**.

Hardware panels (DIO, PWM, …) are under the **Hardware** menu.

## Design notes

**Why bind the HAL instead of WPILib's C++ library?** The HAL is a plain C API, so `bindgen` handles it cleanly. WPILib's C++ classes don't bind well, and porting them line by line would just reproduce Java/C++ design in Rust. rplib builds its own Rust-native layer on top of the HAL instead.

**Why does `run()` take a closure?** Hardware can only be created *after* the HAL is initialized. Taking `|| MyRobot { ... }` lets `run()` initialize first and construct your robot second, so that ordering can't be gotten wrong.

**Why does the runner spawn a thread?** On macOS, GUI code must run on the main thread. When the sim GUI is loaded, it claims the main thread (`HAL_HasMain`), so the robot loop runs on a background thread while the main thread runs the GUI (`HAL_RunMain`). Without the GUI, the loop runs on the main thread directly.

**Shared vs. static linking.** Development builds link the HAL as a shared library so that the sim GUI plugin and your code use the *same* HAL instance. Deployment builds will link statically, producing one self-contained binary.

## Known limitations

- Test mode currently runs `teleop_periodic`.
- Development builds bake an absolute rpath into the binary, so they only run on the machine that built them.
- No vendor library support (CTRE Phoenix, REVLib). CAN motor controllers aren't usable yet; PWM controllers will be.
- WPILib 2027 and Systemcore change the hardware APIs significantly. Expect breaking changes when rplib moves to 2027.
